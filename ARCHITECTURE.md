# xlauncher — архитектура

Спецификация до начала кода. Статус: **согласовано**, версия 3 (после этапа 1).

## 1. Задача

Лаунчер для Windows, который запускает изолированные профили Chromium:

- у каждого профиля свои куки, хранилище, расширения и история;
- у каждого свой отпечаток браузера, устойчивый между запусками и отличающийся от других профилей;
- у каждого свой прокси с проверкой при запуске и историей смены IP;
- профиль переносится на другой компьютер простым копированием папки;
- лаунчером и браузерами можно управлять извне: через API и MCP, в том числе ИИ-агентам — локально и с других машин пользователя;
- изменения из ветки `main` автоматически собираются и устанавливаются без участия человека.

Пользователь один, работает на одном или нескольких своих компьютерах. Одновременная работа нескольких человек с одним профилем не предусматривается.

### Вне задачи

- Командная работа, центральный сервер профилей, раздача доступа.
- Шифрование данных профиля мастер-паролем: сознательно не делаем, защита на уровне диска и учётной записи Windows.
- Интеграция с API прокси-провайдеров и пулы прокси.
- Расширения, устанавливаемые во все профили сразу. Расширения ставятся в каждый профиль вручную.
- Массовая автоматизация действий в соцсетях.

## 2. Процессы и слои

### 2.1 Процессы

```
xlauncher.exe (загрузчик, меняется редко)
   └─ запускает актуальную версию приложения из app\<версия>\
        приложение = окно + REST API + MCP + автоапдейт
           │ запускает и отслеживает
           ▼
   runner (по одному процессу на запущенный профиль)
        прокси-форвардер + мониторинг IP + браузерные инструменты (CDP)
           │ запускает
           ▼
   chrome.exe профиля (fingerprint-chromium)
```

Раннер — отдельный процесс, а не часть приложения. Поэтому приложение можно закрыть, обновить или перезапустить, а открытые браузеры продолжают работать: прокси-форвардер живёт в раннере. После перезапуска приложение находит работающие раннеры по файлам в `run\` и снова подключается к ним.

### 2.2 Слои кода

```
┌───────────────────────────────────────────────────────────┐
│ Интерфейс: HTML/JS в собственном окне (pywebview)          │
└───────────────────────────────────────────────────────────┘
               │ HTTP API                 │ MCP
┌───────────────────────────────────────────────────────────┐
│ Сервер: REST API + MCP (127.0.0.1; по желанию — tailnet)    │
└───────────────────────────────────────────────────────────┘
               │
┌───────────────────────────────────────────────────────────┐
│ Ядро                                                        │
│  profiles    — чтение/запись профилей, миграции схемы       │
│  proxy       — разбор строки, проверка, форвардер           │
│  geo         — IP → страна/город/часовой пояс/провайдер      │
│  fingerprint — генерация параметров в нейтральном формате   │
│  engine      — адаптер движка: параметры → флаги запуска     │
│  portability — ключ шифрования кук, перенос, клоны, локи    │
│  runner      — запуск/остановка, мониторинг IP, CDP         │
│  updater     — проверка и установка обновлений              │
└───────────────────────────────────────────────────────────┘
```

Правило: вся логика живёт в ядре. Интерфейс, API и MCP — тонкие обёртки. Новый способ управления (CLI, Telegram-бот, доступ с телефона) добавляется без правок ядра.

## 3. Хранение

Всё хранится в одной переносной корневой папке, которую пользователь выбирает при первом запуске. В профилях нет абсолютных путей, только относительные от корня.

```
<корень>\
  xlauncher.exe                 загрузчик
  app\
    2026.11.24.1\               текущая версия приложения
    2026.11.23.3\               предыдущая — для отката
    current.txt                 какая версия активна
  settings.json                 общие настройки лаунчера
  engines\
    fingerprint-chromium\
      147.0.xxxx.xx\            несколько версий рядом
      148.0.7778.215\
  geo\
    dbip-city-lite.mmdb         офлайн-база геолокации
    dbip-asn-lite.mmdb
  profiles\
    <slug>\                     имя папки — только подпись, не ID
      profile.json              метаданные, прокси, отпечаток
      ip_history.log            история смены IP (append-only)
      launch.log                журнал запусков
      os_crypt.key              «сырой» ключ шифрования кук (см. §7)
      data\                     --user-data-dir браузера
  cache\
    <profile-id>\               --disk-cache-dir, не переносится
  run\
    <profile-id>.json           работающий раннер: PID, порты, токен
  logs\
  backups\
```

Кэш браузера намеренно вынесен из папки профиля: он занимает сотни мегабайт и не нужен при переносе.

### 3.1 profile.json

```json
{
  "schema": 1,
  "id": "01JD7Q2F3W8K5V0R9N6M4T1XYZ",
  "name": "Пример — Instagram",
  "group": "Пример клиента",
  "notes": "",
  "tags": [],
  "created": "2026-11-24T11:00:00+07:00",

  "proxy": "socks5://user:pass@host:1080",

  "fingerprint": {
    "seed": 2847561093,
    "platform": "windows",
    "brand": "Chrome",
    "hardware_concurrency": 8,
    "locale": "en-US",
    "accept_language": "en-US,en",
    "timezone": "auto"
  },

  "start_urls": ["https://www.instagram.com/"],

  "engine": {
    "name": "fingerprint-chromium",
    "last_version": "148.0.7778.215"
  },

  "agent_access": false,

  "machine": {
    "last_host": "<имя компьютера>",
    "last_launch": "2026-11-24T11:05:00+07:00"
  }
}
```

- `id` — ULID, генерируется один раз. По нему определяются переносы и клоны.
- `schema` — версия формата. Лаунчер мигрирует старые профили при открытии, предварительно сохраняя `profile.json.bak`.
- `proxy` хранится одной строкой, как её вставил пользователь. Логин и пароль прокси лежат здесь же открытым текстом: это осознанное решение, раз шифрования нет.
- `agent_access` — разрешить агентам управлять браузером этого профиля (§8.3).
- Пароли от аккаунтов в `profile.json` не хранятся.

### 3.2 ip_history.log

Строка добавляется только при смене IP. Формат: табы, одна строка — одно событие.

```
2026-11-24 11:05	203.0.113.5	TH	Bangkok	AS64500 Example ISP	launch
2026-11-24 13:40	203.0.113.77	TH	Bangkok	AS64500 Example ISP	monitor
2026-11-25 09:12	198.51.100.4	SG	Singapore	AS64501 Example DC	launch	COUNTRY_CHANGED
```

Последнее поле — источник (`launch`/`monitor`) и необязательная пометка.

### 3.3 settings.json

Общие настройки: движок и версия по умолчанию, интервал мониторинга IP, порт локального API, удалённый доступ (§8.4), канал и интервал обновлений (§9), параметры окна. Данные профилей сюда не попадают.

## 4. Движок и отпечаток

### 4.1 Движок

Первый движок — [fingerprint-chromium](https://github.com/adryfish/fingerprint-chromium):

- основан на ungoogled-chromium: без сервисов Google, синхронизации и телеметрии;
- подменяет отпечаток на уровне исходного кода браузера, управляется флагами запуска;
- собирается под Windows x64, отдельный релиз на каждую мажорную версию Chromium (выходят не все версии подряд);
- содержит защиту от обнаружения автоматизации через CDP и скрывает `navigator.webdriver` — это важно для доступа агентов (§8.3);
- автор не даёт техподдержки, исходники публикуются с задержкой на одну версию.

Зависимость от одного стороннего проекта — риск. Поэтому:

- параметры отпечатка хранятся в нейтральном формате (§3.1) и не привязаны к флагам движка;
- модуль `engine` — адаптер: `fingerprint + proxy + пути → командная строка`. Новый движок = новый адаптер;
- версии движка лежат рядом друг с другом в `engines\`, обновление не затирает старую.

### 4.2 Флаги fingerprint-chromium

Базовый набор по документации проекта:

| Параметр профиля | Флаг | Значение |
|---|---|---|
| `seed` | `--fingerprint=<int>` | 32-битное число; включает большинство подмен (canvas, WebGL, audio, шрифты, clientRects) |
| `platform` | `--fingerprint-platform=windows` | всегда `windows` |
| — | `--fingerprint-platform-version` | не задаём, берётся по умолчанию |
| `brand` | `--fingerprint-brand=Chrome` | без флага браузер представляется как Chromium — редкость у живых пользователей |
| — | `--fingerprint-brand-version` | не задаём: совпадает с реальной версией движка |
| `hardware_concurrency` | `--fingerprint-hardware-concurrency=<int>` | реалистичное значение: 4, 6, 8, 12, 16 |
| `locale` | `--lang=<locale>` | язык интерфейса и `navigator.language` |
| `accept_language` | `--accept-lang=<list>` | заголовок `Accept-Language` |
| `timezone` | `--timezone=<IANA>` | из геолокации IP при `auto` |
| прокси | `--proxy-server=http://127.0.0.1:<порт>` | локальный форвардер раннера (§5.2) |
| — | `--disable-non-proxied-udp` | WebRTC без прямого UDP; в движке включено по умолчанию, передаём явно |

Дополнительно (стандартные флаги Chromium):

```
--user-data-dir=<профиль>\data
--disk-cache-dir=<корень>\cache\<id>
--disable-quic
--no-first-run
--no-default-browser-check
--remote-debugging-port=<порт>         только при доступе агента (§8.3)
--remote-debugging-address=127.0.0.1
```

Флаг `--disable-spoofing` (font, audio, canvas, clientrects, gpu) по умолчанию не используем. Он нужен как аварийный выключатель, если какая-то подмена ломает конкретный сайт.

Не подменяются флагами: размер экрана и `deviceMemory` — у всех профилей на одном компьютере они настоящие.

Адаптер хранит таблицу флагов по версиям движка: флаги могут меняться между версиями (в 144 часть GPU-флагов удалена).

### 4.3 Результаты этапа 1 (Windows 11, ноябрь 2026)

Проверено скриптами `spike/stage1.py` и `spike/canvas_diag.py`.

| Версия | Итог |
|---|---|
| 150.0.7871.186 | **Непригодна.** Подмена canvas роняет вкладку (`getImageData`, текст с юникодом; без GPU — любая выгрузка). browserscan и creepjs падают с «Опаньки». |
| 148.0.7778.215 | **Рабочая, закреплена.** Падений нет. Canvas, audio и WebGL различаются между seed и стабильны для одного seed. |
| 144.0.7559.132 | Ведёт себя как 148. |

Подтверждено на 148:

- WebGL vendor/renderer подменяется и на Windows (профили показывали Intel Iris Xe и NVIDIA RTX 4060 при реальной Intel Arc 140T);
- `navigator.webdriver = false` при управлении через CDP;
- реальный IP не виден ни сайту, ни через WebRTC;
- куки шифруются DPAPI `v10`, app-bound ключа нет; перенос с восстановлением ключа сохраняет куки (§7.1).

Известные проблемы движка (во всех проверенных версиях):

- `CanvasRenderingContext2D.measureText()` с включённой подменой canvas возвращает ширину около нуля. Это заметно антибот-проверкам и может ломать сайты, которые меряют текст на canvas. Принято как известный риск; отключение подмены canvas (`--disable-spoofing=canvas`) лечит, но делает canvas одинаковым у всех профилей.
- У подмены audio мало вариантов: разные seed иногда дают одинаковое значение или совпадают с реальным. При создании профиля лаунчер делает короткий проверочный запуск и перегенерирует seed, если audio или canvas совпали с другим профилем или с «чистым» браузером.

### 4.4 Обновление движка

Новая версия движка не включается автоматически только потому, что вышла. Порядок:

1. лаунчер скачивает новую версию в `engines\`;
2. прогоняет на ней диагностику (аналог `spike/canvas_diag.py`): падения вкладок, различие и стабильность canvas/audio/WebGL;
3. только если диагностика чистая, версия становится версией по умолчанию; иначе остаётся закреплённая, а в интерфейсе — предупреждение.

### 4.5 Версии и откат

Профиль, открытый новой версией Chromium, может сломаться в старой. Правила:

- в `profile.json` записывается `engine.last_version`;
- запуск версией **ниже** `last_version` запрещён (с объяснением, какую версию поставить);
- при переносе на компьютер, где нужной версии нет, лаунчер скачивает её.

Обновление движка — отдельно от обновлений лаунчера (§9.5).

### 4.6 Генерация отпечатка

При создании профиля:

- `seed` — случайное 32-битное число;
- `platform` — всегда `windows` (работаем на Windows; подмена ОС палится шрифтами и рендерингом);
- `brand` — `Chrome`;
- `hardware_concurrency` — случайно из реалистичных значений;
- `locale` и `accept_language` — по стране прокси на момент создания, дальше фиксированы.

После создания отпечаток не меняется. Исключение — команда «Клонировать» (§7.3).

При создании — проверочный запуск: seed перегенерируется, если canvas или audio совпали с другим профилем или с браузером без подмены (§4.3).

### 4.7 Часовой пояс

`timezone: "auto"` — часовой пояс определяется по текущему IP при каждом запуске. Можно задать фиксированный пояс вручную.

### 4.8 Проверка отпечатка

Кнопка «Проверить профиль» открывает в профиле сайты проверки (browserleaks, creepjs, browserscan, pixelscan) для визуальной оценки.

## 5. Прокси

### 5.1 Формат

Пользователь вставляет одну строку. Поддерживаются:

```
socks5://user:pass@host:port
http://user:pass@host:port
host:port:user:pass          (по умолчанию socks5)
host:port                    (без авторизации)
```

Привязки прокси к профилю «навсегда» нет: строку можно заменить в любой момент, ротация на стороне прокси допустима. Пулов и интеграции с провайдерами нет.

### 5.2 Локальный форвардер

Chromium не умеет передавать логин и пароль прокси через флаг `--proxy-server`. Поэтому раннер каждого профиля поднимает форвардер:

```
Chromium ──HTTP CONNECT host:port──▶ 127.0.0.1:<порт> ──SOCKS5/HTTP + auth──▶ прокси ──▶ сайт
```

- форвардер передаёт апстриму **имя хоста**, а не IP: DNS-запросы разрешаются на стороне прокси;
- порт выбирается свободный на каждый запуск;
- форвардер живёт в раннере и не зависит от перезапусков приложения (§2.1).

### 5.3 Проверка при запуске

Перед запуском браузера раннер через тот же форвардер:

1. проверяет, что прокси отвечает (таймаут, ошибка авторизации);
2. получает внешний IP;
3. определяет страну, город, часовой пояс, провайдера (§6).

Результаты:

- прокси не работает → **алярм**, браузер не запускается (без прокси профиль засветит реальный IP);
- IP сменился → строка в `ip_history.log`;
- сменилась страна → строка с пометкой `COUNTRY_CHANGED` и предупреждение с выбором «Запустить» / «Отмена».

### 5.4 Мониторинг во время работы

Пока профиль открыт, раннер раз в N минут (по умолчанию 10) проверяет внешний IP через форвардер. Смена IP записывается в историю с источником `monitor`. Если сменилась страна или прокси перестал отвечать, показывается уведомление.

### 5.5 Защита от утечек мимо прокси

- WebRTC: без прямого UDP (`--disable-non-proxied-udp`);
- QUIC/HTTP3 отключён (`--disable-quic`): UDP не идёт через прокси;
- DNS разрешается на стороне прокси (§5.2);
- сервисы Google, синхронизация, телеметрия отсутствуют в ungoogled-chromium.

Проверка: browserleaks.com/webrtc и dnsleaktest в профиле не должны показывать реальный IP.

## 6. Геолокация IP

- Основной источник — офлайн-база [DB-IP City Lite](https://db-ip.com/db/download/ip-to-city-lite) (формат mmdb, лицензия CC BY 4.0, скачивается без ключа). Обновляется автоматически раз в месяц.
- Провайдер/ASN — DB-IP ASN Lite.
- Резервный источник — онлайн-сервис, если в офлайн-базе нет данных.

## 7. Перенос, клоны и блокировки

### 7.1 Перенос копипастом и шифрование кук

На Windows Chromium шифрует куки и сохранённые пароли AES-ключом. Сам ключ лежит в `data\Local State` и зашифрован средствами Windows (DPAPI) — привязан к пользователю Windows. Если просто скопировать профиль на другой компьютер, ключ не расшифруется и все сессии потеряются.

Решение:

1. При первом успешном запуске профиля лаунчер расшифровывает ключ и сохраняет его в `os_crypt.key` в папке профиля.
2. Перед каждым запуском лаунчер проверяет, расшифровывается ли ключ в `Local State` на текущем компьютере.
3. Если нет (профиль перенесён), лаунчер шифрует ключ из `os_crypt.key` под текущего пользователя Windows и записывает его в `Local State`.

В результате перенос — просто копирование папки профиля.

`os_crypt.key` хранится открытым: кто получил папку профиля, получил доступ к аккаунтам. Это соответствует решению не шифровать данные (§1).

Новейшие версии брендированного Google Chrome используют дополнительную привязку ключа к самому приложению, которая сломала бы эту схему. В ungoogled-chromium её нет. На этапе 1 (§12) это подтверждается одним тестом: перенос профиля между двумя учётками Windows.

### 7.2 Обнаружение переноса

Признаки: `machine.last_host` не совпадает с текущим компьютером, ключ в `Local State` не расшифровывается. Лаунчер выполняет §7.1, при необходимости скачивает нужную версию движка (§4.5) и обновляет `machine`.

### 7.3 Клоны

Если в `profiles\` два профиля с одинаковым `id`, лаунчер блокирует их запуск и спрашивает:

- **Это копия для переноса** → одна из папок удаляется пользователем вручную;
- **Это новый профиль** → у копии генерируются новые `id` и `seed`, удаляются куки, история, `os_crypt.key` и `Local State`. Остаются расширения, закладки и настройки.

Команда «Клонировать» в интерфейсе делает то же самое сразу. Два профиля с одинаковым отпечатком для сайтов выглядят как один человек с двумя аккаунтами — этого нужно избегать.

### 7.4 Блокировки

- Профиль нельзя запустить, если для него уже работает раннер.
- После аварийного завершения или копирования открытого профиля остаются lock-файлы Chromium (`SingletonLock`, `SingletonCookie`, `SingletonSocket`) и устаревшие файлы в `run\`. Если процесса нет, лаунчер их удаляет.
- Копировать профиль во время работы браузера нельзя: базы могут повредиться. Лаунчер предупреждает об этом в интерфейсе.

## 8. Внешнее управление

### 8.1 REST API

Слушает `127.0.0.1` (и, по желанию, адрес в tailnet — §8.4). Основные методы:

```
GET    /api/profiles
POST   /api/profiles                 создать (имя, группа, строка прокси, стартовые URL)
POST   /api/profiles/import          массовый импорт CSV / текст
GET    /api/profiles/{id}
PATCH  /api/profiles/{id}
DELETE /api/profiles/{id}            удаление в корзину (backups\)
POST   /api/profiles/{id}/clone
POST   /api/profiles/{id}/start      параметры: agent_access
POST   /api/profiles/{id}/stop
POST   /api/profiles/{id}/check-proxy
GET    /api/profiles/{id}/ip-history
GET    /api/status                   запущенные профили, ошибки, версия, обновления
```

### 8.2 MCP

MCP-сервер встроен в приложение. Транспорты:

- **stdio** — для агентов на этом же компьютере (Claude Desktop и Claude Code на Windows);
- **Streamable HTTP** — для агентов с других машин через tailnet (§8.4).

Инструменты управления лаунчером:

```
list_profiles, get_profile, create_profile, update_profile,
start_profile, stop_profile, check_proxy, get_ip_history, get_status
```

### 8.3 Управление браузером агентом

Браузерные инструменты встроены в тот же MCP, а не подключаются отдельным сервером. Причина: адрес отладки (CDP) у профиля меняется при каждом запуске, а встроенные инструменты сами находят нужный профиль по ID. Агенту не нужно настраивать подключение.

```
browser_tabs(profile)                    список вкладок
browser_navigate(profile, url)
browser_snapshot(profile)                текст и структура страницы с ссылками на элементы
browser_screenshot(profile)
browser_click(profile, element)
browser_type(profile, element, text)
browser_press_key(profile, key)
browser_scroll(profile, ...)
browser_wait(profile, ...)
```

Реализация: раннер подключается к CDP своего браузера (Playwright `connect_over_cdp`) и выполняет команды. Сам порт отладки наружу не публикуется — он слушает только `127.0.0.1`, а агенты работают через MCP.

Правила доступа:

- браузерные инструменты работают только для профилей с `agent_access: true` и только пока профиль запущен с этим флагом;
- профиль с включённым доступом агента помечается в интерфейсе;
- все действия агента записываются в `launch.log` профиля.

Ограничения:

- доступ агента = полный контроль над залогиненными аккаунтами;
- автоматизацию можно обнаружить по косвенным признакам, хотя движок скрывает основные (§4.1). Сценарий — отдельные действия с участием человека, не массовые операции.

### 8.4 Удалённый доступ

Для агентов на других машинах пользователя (например, Claude Code на Ubuntu-сервере):

- в `settings.json` включается прослушивание адреса в tailnet ([Tailscale](https://tailscale.com)). В открытый интернет сервер не слушает никогда;
- все запросы не с `127.0.0.1` требуют токен (`Authorization: Bearer …`). Токен генерируется в настройках, хранится в `settings.json`, показывается один раз для копирования;
- MCP по Streamable HTTP с тем же токеном;
- CDP наружу не публикуется (§8.3).

### 8.5 Какие агенты что могут

| Агент | Как подключается | Управление лаунчером | Управление браузером |
|---|---|---|---|
| Claude Code / Claude Desktop на этом Windows | MCP stdio | да | да |
| Claude в облачной сессии, связанной с этим компьютером через приложение Claude Desktop | локальный MCP, который приложение пробрасывает в сессию | да | да |
| Claude Code на другой машине (Ubuntu и т. п.) | MCP по HTTP через tailnet + токен | да | да |

## 9. Автоматические обновления

Цель: изменения в `main` попадают на все компьютеры пользователя без его участия.

### 9.1 Сборка

GitHub Actions на каждый push в `main`:

1. тесты (ядро, разбор прокси, генерация отпечатка, миграции профилей);
2. сборка пакета приложения на Windows-раннере;
3. публикация GitHub Release с версией `ГГГГ.ММ.ДД.N`, архивом пакета и его SHA-256.

Если тесты не прошли, релиз не создаётся и до компьютеров ничего не доходит.

### 9.2 Пакет

- **Загрузчик** `xlauncher.exe` — маленький, меняется редко. Читает `app\current.txt`, запускает нужную версию, откатывает при сбое (§9.4).
- **Приложение** — папка `app\<версия>\`: встроенный Python (embeddable), зависимости и код. Обновление — новая папка рядом, а не замена работающих файлов.

Такой формат обходит проблему Windows «нельзя перезаписать запущенный `.exe`», делает обновления небольшими и сохраняет предыдущую версию для отката.

### 9.3 Установка

- Приложение проверяет релизы при старте и раз в 15 минут.
- Найдена новая версия → скачивает архив, сверяет SHA-256, распаковывает в `app\<новая>\`.
- Переключает `current.txt` и перезапускается сразу, без подтверждения. Открытые браузеры не затрагиваются: они живут в раннерах (§2.1).
- Раннеры уже открытых профилей продолжают работать на старом коде и обновляются при следующем запуске профиля. Протокол приложение ↔ раннер версионируется, приложение поддерживает текущую и предыдущую версию протокола.
- Окно показывает короткое уведомление «Обновлено до версии …».

### 9.4 Откат

- Если новая версия не запустилась или не ответила на проверку работоспособности за 30 секунд, загрузчик возвращает предыдущую версию и помечает новую как сбойную. Повторно она не ставится, пока не выйдет следующий релиз.
- Миграции `profile.json` (§3.1) сохраняют `.bak` и должны оставлять профиль читаемым для предыдущей версии приложения, либо версия схемы повышается только вместе с явным предупреждением в релизе.
- В приложении хранятся две последние версии.

### 9.5 Что обновляется отдельно

- **Движок** (fingerprint-chromium): новая версия скачивается автоматически и становится версией по умолчанию только после чистой диагностики (§4.4); профили переходят на неё при следующем запуске, без отката (§4.5).
- **Геобаза**: раз в месяц, в фоне.

### 9.6 Безопасность обновлений

Репозиторий публичный, релизы тоже. Секретов в сборке нет. Скачивание — только с GitHub Releases этого репозитория по HTTPS со сверкой SHA-256.

Важно: автообновление означает, что код из `main` исполняется на компьютерах пользователя автоматически. Защита аккаунта GitHub (2FA, ограничение прав на push) становится защитой этих компьютеров.

## 10. Интерфейс

HTML/JS-страница, отображаемая в собственном окне через pywebview. Те же страницы открываются в обычном браузере по адресу локального API.

Экраны:

- **Список профилей** по группам: статус (запущен/нет, доступ агента), текущий IP и страна, последний запуск, кнопки «Запустить», «Стоп», «Проверить».
- **Новый / редактирование профиля**: имя, группа, строка прокси (с кнопкой «Проверить»), стартовые URL, заметки, доступ агента, отпечаток (только просмотр + «Перегенерировать» для нового профиля).
- **Карточка профиля**: история IP, журнал запусков и действий агента, путь к папке, кнопки «Клонировать», «Открыть папку», «Проверить отпечаток».
- **Импорт**: вставка CSV/текста, предпросмотр, проверка прокси пачкой.
- **Настройки**: версии движка, интервал мониторинга, порт API, удалённый доступ и токен, обновления (текущая версия, история, откат вручную).

## 11. Технологии

- Python 3.13 (embeddable на Windows), асинхронное ядро (asyncio).
- Сервер: FastAPI + uvicorn.
- MCP: официальный Python SDK (stdio + Streamable HTTP).
- Браузерные инструменты: Playwright (`connect_over_cdp`), без установки браузеров Playwright.
- Форвардер прокси: своя реализация на asyncio (HTTP CONNECT на входе; SOCKS5/HTTP с авторизацией на выходе).
- DPAPI: `ctypes` (CryptProtectData/CryptUnprotectData).
- Геолокация: `maxminddb`.
- Окно: pywebview (WebView2 на Windows).
- Загрузчик: Go, один `.exe` без зависимостей (~6 МБ), собирается в CI кросс-компиляцией. Неподписанный `.exe` может вызывать предупреждение SmartScreen — достаточно разрешить один раз.
- CI: GitHub Actions — сборка на `ubuntu-latest` (пакет под Windows собирается `pip --platform win_amd64`), self-test пакета на `windows-latest`.

## 12. Этапы

1. ~~**Проверка рисков**~~ — выполнено, результаты в §4.3.
2. **Автообновления в первую очередь:** загрузчик, CI, релизы, установка и откат (§9). Всё дальнейшее приходит на компьютеры уже через автообновление.
3. **Ядро + раннер:** профили, прокси, проверки, история IP, запуск/остановка, клоны, блокировки.

6. **Импорт**, загрузчик движка и геобазы, мелочи интерфейса.

## 13. Размещение

Сейчас — рабочий Windows-ПК пользователя. Перенос на выделенный сервер (VPS) возможен позже без изменений архитектуры: профили переносятся копированием папки (§7), удалённый доступ — через tailnet (§8.4).

Риск VPS, который нужно проверить до переезда: на сервере нет видеокарты, и браузер показывает сайтам программный рендерер WebGL — типичный признак виртуальной машины. Проверяется тем же скриптом этапа 1 (`spike/`) на самом сервере.
